**Snowflake Semantic Views read from the account alone: `semantic.deployment: snowflake_account`.** Under `semantic.vendor: snowflake`, the new deployment reads the catalog from every semantic view in the source allowlist's scopes, with no repository file needed: a warehouse-free `SHOW SEMANTIC VIEWS` per scope, then `SYSTEM$READ_YAML_FROM_SEMANTIC_VIEW` per view, each read-back checked by the same validator that reads a file. It is the Snowflake counterpart of `dbt_cloud` and, like it, is read only by `explore semantic list|values|query` and by `explore relationships|map --use-hosted-semantic-layer`, which now fold in the account's keys and joins on their base tables. Dex still renders `SEMANTIC_VIEW(...)` and runs it through its own Snowflake connector (`execution: dex`), so the cost guard, the source allowlist and the PII gate apply exactly as under `local`. What changes is trust. The deployed definition is the only one, so nothing is checked against a file, and every result says so: `list` carries `source: account`, `query` and `values` carry `definition_source: account`, and each carries a warning. `coverage` names every view: `full`; `limited`, where a read-back reads a member it does not carry; or `refused`, for a read-back that was refused or failed validation, or for a name held in two allowlisted scopes, with both copies named and `--scope` suggested. The deployment is opt-in only and never a fallback when `semantic.snowflake.files` is empty. Configured files stay optional and keep serving `maintain`, `transform`, `--use-project` and `--local`, which checks the deployment against them. A deployed view that a configured file describes is named on its result (`repository_file`), takes the file's spelling, and is never silently passed over.
